# Decisions log

Choices made where the PRD was silent or ambiguous. Format: date — decision — reason.
Open decisions from PRD §13 are **not** decided here; they are asked of the maintainer.

| Date | Decision | Reason |
|---|---|---|
| 2026-11-10 | API functions are declared `external`; constants are plain `const int` with Arduino.h values. | `external` gives analyzable signatures with no fake bodies to maintain. Plain `int` (vs. distinct extension types per kind) is the simpler option and matches Arduino's own typing; stricter typing can come later without breaking user code. |
| 2026-11-10 | Arduino spelling is kept (`INPUT_PULLUP`, `digitalWrite`); `constant_identifier_names` is ignored in `arduino_core.dart` only. | Code reads the same in Dart, tutorials, and generated C++. Scoping the ignore to one file keeps the lint active everywhere else. |
| 2026-11-10 | Diagnostics print the PRD §9.6 header line, then the suggestion on a second line as `  = help: …`. | Keeps the machine-parsable `file:line:col: error[Exxx]: message` header unambiguous while still always showing a suggestion. |
| 2026-11-10 | Diagnostic locations and `#line` directives use the source file's basename, not an absolute path. | Output must be byte-identical across machines (determinism, goldens). Matches the PRD's `#line 3 "blink.dart"` example. |
| 2026-11-10 | Diagnostics are sorted by (line, column, code) before printing. | Deterministic output independent of which validator rule ran first. |
| 2026-11-10 | Generated sketches start with a one-line `// Generated by unodar from <file>. Do not edit…` comment; functions are emitted in source order. | Tells readers where the code came from (readable, traceable output, G4). No version number in the header, so goldens don't churn on every release. Source order keeps `#line` values monotonic. |
| 2026-11-10 | IR carries C++ names; the Dart→C++ mapping happens once, during lowering, via the API registry. | Keeps the emitter a dumb printer with no knowledge of Dart names, so interop bindings (Phase 3) only touch the registry and lowering. |
| 2026-11-10 | If the analyzer reports any error (E007), compilation stops before validation. | A source with type/syntax errors yields an unreliable AST; validating it would add misleading follow-on diagnostics on top of the real problem. |
| 2026-11-10 | API calls and constants are matched by **resolved element** (declared in `package:unodar`), not by name. | A user's own `delay()` or one from another package must never silently compile to Arduino's `delay`. |
| 2026-11-10 | Imports other than unprefixed `package:unodar/unodar.dart`, and `export`/`part` directives, are E005. | The PRD lists no code for directives; E005 ("unsupported top-level declaration") is the closest fit. |
| 2026-11-10 | Arguments to an unknown function (E003) are not also checked for E004. | The call is wrong as a whole; reporting its arguments too is noise. |
| 2026-11-10 | Lowering lives in its own `lib/src/lowering/` (and the API table in `lib/src/api/`), beside the PRD's listed dirs. | Keeps the IR library free of analyzer imports and makes the registry usable by validator and lowering alike. |
| 2026-11-10 | An analyzer "undefined name" error located exactly at the name of a bare call statement in `setup`/`loop` (e.g. `tone(8, 440);`) is reported as E003, not E007. Any other analyzer error still stops compilation, and then *all* analyzer errors are shown as E007. | The PRD's own E003 example (`tone`) is an undefined function, which the analyzer flags first. Matching by source position rather than by analyzer error-code name survives analyzer upgrades. If no validator rule explains a deferred error, it is still reported (E007), so nothing slips through. |
| 2026-11-10 | CLI usage errors (missing/unknown command, bad flags) and unreadable input exit with **2**, not 1. | PRD §9.6 reserves 1 for diagnostics in the user's source; anything else is tooling. Lets scripts tell "fix your Dart" apart from "fix the invocation". |
| 2026-11-10 | `build -o` defaults to `build/` when omitted. | The PRD shows `-o` but not whether it is required; a default is the simpler UX. `build/` is git-ignored. |
| 2026-11-10 | The CLI is hand-rolled on `ArgParser` rather than `CommandRunner`. | `CommandRunner` prints usage via `print`, which can't be captured for in-process tests; one command does not justify the indirection. |
| 2026-11-10 | After diagnostics, the CLI prints a count line (`2 errors.`). | Makes it obvious the list is complete when several problems are reported. |
| 2026-11-10 | Size budgets live in `test/size_budgets.dart` (per golden case: baseline + hard max) and are read from `arduino-cli --format json` (`text` = flash, `data` = RAM). | Structured output instead of scraping the human-readable size line. A dedicated file makes budget changes stand out in review, and only commits that explain the change should touch it. |
| 2026-11-11 | **PRD §13.1 decided by the maintainer:** Dart `int` → `int32_t`, `double` → `float`, `bool` → `bool` on every target. Sized `Uint8`/`Uint16`/`Int16` extension types in `package:unodar` map to `uint8_t`/`uint16_t`/`int16_t`. | One `int` width on Uno and ESP32 keeps programs portable, and 32 bits covers `millis()`-style values. Overflow behaviour differs from Dart's 64-bit `int` and is documented in SUBSET.md "Known deviations from Dart". |
| 2026-11-11 | Sized types are `extension type const Uint8._(int) implements int` with a wrapping `const Uint8(int v)` constructor. Reading widens to `int`; arithmetic yields `int`; storing back needs an explicit `Uint8(...)`. | The Dart side is real, executable, and tested, and it wraps exactly like the C++ conversion. Making implicit truncation a Dart type error means a value never changes width invisibly. |
| 2026-11-11 | `/` on ints is **implemented** as `float(a) / float(b)` (a `double` result, as in Dart), not rejected. | Dart's type checker already forbids storing the result in an `int` (E007, suggesting `~/`), so the C mistake of truncating division cannot happen silently. Precision is the documented `double` → `float` deviation. |
| 2026-11-11 | `~/` on ints compiles to C++ `/`; `%` on ints compiles to a `constexpr unodar_mod(a, b)` helper with Dart's non-negative result, emitted only when used. `%`/`~/` on doubles are rejected (E002). | Both C++11 and Dart truncate `~/` toward zero. Rejecting `%` would break the common `i % 2 == 0`. A helper inside the `.ino` keeps single-file output (PRD §13.2 untouched); `constexpr` keeps it usable in constant initializers. |
| 2026-11-11 | The IR holds expression trees without parentheses; the emitter inserts them from C++ precedence and associativity. | The Dart parser's tree is the authority, so the output regroups correctly even where Dart and C++ precedence tables differ. |
| 2026-11-11 | Every `int` operation is computed in `int32_t`: when both operands would be narrower than 32 bits in C++ (literals and sized values on the 16-bit-`int` Uno), the emitter widens one with an `L` suffix or `int32_t(...)`. The native `int` width comes from the `Target`. | On AVR, plain C++ `60 * 1000` wraps to -5536. Widening only where needed keeps blink's output and most code unchanged. |
| 2026-11-11 | All-constant subexpressions are evaluated at compile time with Dart semantics; any intermediate value outside `int32_t`, or a constant division by zero, is E010. Runtime overflow and runtime division/`%` by zero are documented deviations with no checking helper (maintainer decision). | Catches every case that is knowable at compile time loudly; a runtime check would cost flash and invent behaviour Dart doesn't have on a device without exceptions. |
| 2026-11-11 | Assignments, `++`, and `--` are statements only (plus `for` updaters). Inside one operator's operands, one argument list, or the two sides of `+=`/`-=`, a user-function call may not sit next to another call or a read of a mutable top-level variable (E013). | Dart evaluates left to right; C++ leaves that order unspecified. This conservative rule is simple to explain and always has a fix (a local). It can be relaxed later with purity analysis. |
| 2026-11-11 | Only `+=` and `-=` among compound assignments; `*=`, `~/=`, `%=`, and the bitwise forms are E002. Bitwise and shift operators are E002. | Matches the Phase 2 scope exactly. Shifts in particular differ (negative counts, counts ≥ 32, `>>>`) and need their own fidelity work. |
| 2026-11-11 | `==`/`!=` between a `bool` and a number is E009. | Dart: never equal. C++: `true == 1`. |
| 2026-11-11 | Dart `const` → `constexpr`, `final` → `const`, mutable → plain, for globals and locals. Top-level initializers must be Dart constant expressions over earlier `const` declarations (E015); forward references are rejected rather than reordered. | `constexpr` is exactly Dart `const`, and it lets the fidelity test `static_assert` values. Rejecting forward references keeps source order (monotonic `#line`) and C++ declare-before-use without a dependency sort. |
| 2026-11-11 | Locals (any initializer, `var`/`final` typed from the resolved type), nested blocks, and unlabeled `break`/`continue` are allowed; labeled ones are rejected (maintainer decision). Nullable types are E009. | Needed for `for` loops and real programs; their C++ meaning is identical. |
| 2026-11-11 | The registry models named parameters, but they are enabled and tested in Phase 3; a named argument to an API function is E004 until then (maintainer decision). Today the analyzer reports such calls first (E007), since no API function declares named parameters. | Nothing in the Phase 2 API takes named parameters, and a fake API package would add test-only plumbing to the resolver. |
| 2026-11-11 | Constant API arguments are range-checked against the Arduino C++ parameter type (E004, e.g. pin `-13` for `uint8_t`); non-constant ones are converted by C++ rules (documented deviation). | The registry now records each parameter's C++ type, so the check is data-driven. |
| 2026-11-11 | Reserved names (E014) = C++ keywords + every API registry name + a static Arduino core/avr-libc deny-list on `UnoTarget` + ALL-CAPS names + C/C++/unodar reserved patterns (`_t` suffix, `__`, `$`, `_` + upper-case, `unodar_`). Applies to user declarations only (maintainer decision). | Arduino.h defines function-like macros (`min`, `abs`, `round`, …) and the AVR headers define hundreds of upper-case macros; a colliding user name would be macro-substituted, a silent miscompile. |
| 2026-11-11 | Generated layout: header, includes, used helpers, prototypes for all user functions except `setup`/`loop`, globals in source order, functions in source order. Prototypes and helpers come before the first `#line`. | Explicit prototypes make call order independent of arduino-cli's prototype generator; lines with no Dart source keep their real `.ino` line numbers. |
| 2026-11-11 | E004 now means "argument the API cannot accept" (out of range or named); E002 covers unsupported expressions everywhere, including in arguments. Codes are not renumbered. | Phase 2 allows any expression as an argument, so E004's Phase 1 meaning ("only literals and constants") no longer exists; its title "Unsupported argument" still fits. |
| 2026-11-11 | Recursion, direct or mutual, is rejected (E016) by a cycle check over the call graph of all user functions including `setup`/`loop`; each cycle is reported once, at its first function in source order, with the path (maintainer decision, replacing the earlier "known deviation"). | Dart throws `StackOverflowError`; the Uno's 2 KB stack would silently overwrite globals. Rejecting the cycle is the only way to keep the fidelity rule. Without recursion, worst-case stack depth is also statically bounded, which later phases can measure. |
