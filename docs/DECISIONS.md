# Decisions log

Choices made where the PRD was silent or ambiguous. Format: date — decision — reason.
Open decisions from PRD §13 are **not** decided here; they are asked of the maintainer.

| Date | Decision | Reason |
|---|---|---|
| 2026-11-10 | API functions are declared `external`; constants are plain `const int` with Arduino.h values. | `external` gives analyzable signatures with no fake bodies to maintain. Plain `int` (vs. distinct extension types per kind) is the simpler option and matches Arduino's own typing; stricter typing can come later without breaking user code. |
| 2026-11-10 | Arduino spelling is kept (`INPUT_PULLUP`, `digitalWrite`); `constant_identifier_names` is ignored in `arduino_core.dart` only. | Code reads the same in Dart, tutorials, and generated C++. Scoping the ignore to one file keeps the lint active everywhere else. |
| 2026-11-10 | Diagnostics print the PRD §9.6 header line, then the suggestion on a second line as `  = help: …`. | Keeps the machine-parsable `file:line:col: error[Exxx]: message` header unambiguous while still always showing a suggestion. |
| 2026-11-10 | Diagnostic locations and `#line` directives use the source file's basename, not an absolute path. | Output must be byte-identical across machines (determinism, goldens). Matches the PRD's `#line 3 "blink.dart"` example. |
| 2026-11-10 | Diagnostics are sorted by (line, column, code) before printing. | Deterministic output independent of which validator rule ran first. |
| 2026-11-10 | Generated sketches start with a one-line `// Generated by unodar from <file>. Do not edit…` comment; functions are emitted in source order. | Tells readers where the code came from (readable, traceable output, G4). No version number in the header, so goldens don't churn on every release. Source order keeps `#line` values monotonic. |
| 2026-11-10 | IR carries C++ names; the Dart→C++ mapping happens once, during lowering, via the API registry. | Keeps the emitter a dumb printer with no knowledge of Dart names, so interop bindings (Phase 3) only touch the registry and lowering. |
| 2026-11-10 | If the analyzer reports any error (E007), compilation stops before validation. | A source with type/syntax errors yields an unreliable AST; validating it would add misleading follow-on diagnostics on top of the real problem. |
| 2026-11-10 | API calls and constants are matched by **resolved element** (declared in `package:unodar`), not by name. | A user's own `delay()` or one from another package must never silently compile to Arduino's `delay`. |
| 2026-11-10 | Imports other than unprefixed `package:unodar/unodar.dart`, and `export`/`part` directives, are E005. | The PRD lists no code for directives; E005 ("unsupported top-level declaration") is the closest fit. |
| 2026-11-10 | Arguments to an unknown function (E003) are not also checked for E004. | The call is wrong as a whole; reporting its arguments too is noise. |
| 2026-11-10 | Lowering lives in its own `lib/src/lowering/` (and the API table in `lib/src/api/`), beside the PRD's listed dirs. | Keeps the IR library free of analyzer imports and makes the registry usable by validator and lowering alike. |
| 2026-11-10 | An analyzer "undefined name" error located exactly at the name of a bare call statement in `setup`/`loop` (e.g. `tone(8, 440);`) is reported as E003, not E007. Any other analyzer error still stops compilation, and then *all* analyzer errors are shown as E007. | The PRD's own E003 example (`tone`) is an undefined function, which the analyzer flags first. Matching by source position rather than by analyzer error-code name survives analyzer upgrades. If no validator rule explains a deferred error, it is still reported (E007), so nothing slips through. |
| 2026-11-10 | CLI usage errors (missing/unknown command, bad flags) and unreadable input exit with **2**, not 1. | PRD §9.6 reserves 1 for diagnostics in the user's source; anything else is tooling. Lets scripts tell "fix your Dart" apart from "fix the invocation". |
| 2026-11-10 | `build -o` defaults to `build/` when omitted. | The PRD shows `-o` but not whether it is required; a default is the simpler UX. `build/` is git-ignored. |
| 2026-11-10 | The CLI is hand-rolled on `ArgParser` rather than `CommandRunner`. | `CommandRunner` prints usage via `print`, which can't be captured for in-process tests; one command does not justify the indirection. |
| 2026-11-10 | After diagnostics, the CLI prints a count line (`2 errors.`). | Makes it obvious the list is complete when several problems are reported. |
| 2026-11-10 | Size budgets live in `test/size_budgets.dart` (per golden case: baseline + hard max) and are read from `arduino-cli --format json` (`text` = flash, `data` = RAM). | Structured output instead of scraping the human-readable size line. A dedicated file makes budget changes stand out in review, and only commits that explain the change should touch it. |
